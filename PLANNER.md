# Этап 1: планировщик рабочего дня

Планировщик добавлен в существующий проект. Рабочий бот, его Bitrix-клиент,
`access.db`, серверная `.env`, `Dockerfile` и `compose.yaml` продолжают использоваться
как раньше. Само добавление файлов ничего не развёртывает и не перезапускает.

## Что добавлено

- `planner/`: FastAPI, проверка Telegram initData, модели запросов, SQLite и правила доступа.
- `miniapp/`: React + TypeScript + Vite, интерфейсы менеджера и руководителя,
  светлая/тёмная тема Telegram, мобильное меню, диалоги и обработка ошибок.
- `requirements-planner.txt`: дополнительные Python-зависимости; зависимости бота отдельно.
- `compose.planner.yaml`, `deploy/Planner.Dockerfile`, его отдельный dockerignore
  и пример Nginx: самостоятельный сервис на **том же VPS**.
- `tests/test_planner.py`: тесты API и правил работы на временных базах.
- `tests/planner_browser_server.py`, `miniapp/tests/ui.cjs`: локальный браузерный тест.
- `miniapp/preview.html`: демонстрация интерфейса только через Vite dev server.

Изменены `config.py`, `keyboards.py`, `bot.py`: необязательный `MINI_APP_URL`,
кнопка «Мой план дня» в личном `/start` и команда `/plan`. При пустом URL старый
сценарий работает без Mini App. Кнопки WebApp в группах не отправляются; `/plan`
предлагает перейти в личный чат. Также обновлены `.env.example`, `.gitignore`, README
и тесты подключения бота. Рабочая `.env` не редактировалась.

## Роли и доступ

При создании **новой** базы планировщика создаются:

| Имя | Telegram ID | Bitrix24 ID | Роль |
| --- | --- | --- | --- |
| Вячеслав | 8306778724 | 460 | manager |
| Яна | 7939114214 | 110 | manager |
| Руководитель | 1073597301 | — | supervisor |

При повторном запуске эти записи не перезаписываются. Руководитель может создать
нового менеджера, проверить привязку Telegram ID Яны и отключить сотрудника в «Менеджеры».
Добавлять руководителей через публичный API нельзя. Роль администратора бота
**не** даёт роль supervisor: даже администратору нужна отдельная запись Mini App.

При каждом API-запросе одновременно проверяются:

1. Подпись `Telegram.WebApp.initData` по HMAC-SHA256 с существующим BOT_TOKEN.
2. Возраст подписи: до 12 часов, допуск будущего времени 30 секунд.
3. Доступ в существующем боте: `allowed_users` или `ADMIN_TELEGRAM_IDS`.
4. Активный сотрудник планировщика, его роль и принадлежность конкретного объекта.

Поэтому администратор существующего бота должен предварительно выполнить
`/adduser 1073597301` и `/adduser 8306778724`, если этих людей ещё нет в доступе.
Для Яны нужны **оба** условия: привязка ID 7939114214 к Bitrix24 ID 110 в
Mini App и `/adduser 7939114214` администратором бота. Не добавляйте руководителя в
`ADMIN_TELEGRAM_IDS` только ради роли Mini App.

Удаление через `/removeuser` начинает действовать и в Mini App со следующего
запроса, кроме администраторов бота. Существующее правило бота сохраняется:
ID из `ALLOWED_TELEGRAM_IDS` импортируются повторно при запуске бота.

InitData передаётся только в заголовке `Authorization: tma ...`, не в URL и не
в localStorage. Frontend не содержит токенов или webhook. Нет режима обхода
проверок production-API. Через 12 часов приложение нужно закрыть и открыть из
Telegram заново. Подпись не является одноразовой: её срок ограничен, транспорт — HTTPS.

## Правила планирования

- Дата и «сегодня» определяются backend по Europe/Moscow. График 10:00–19:00 отображается в интерфейсе; после 19:00 редактирование разрешено. Новые напоминания не включены.
- Один план на сотрудника и дату. До 100 задач в плане.
- Время планируется в минутах; таймер хранит секунды и серверную метку начала.
- Запустить таймер можно только на своей незавершённой задаче сегодняшнего дня.
  Пауза/стоп сохраняют накопленное время, повторный старт продолжает его.
  Закрытие окна не останавливает таймер. Два таймера блокируются транзакцией и
  уникальным индексом SQLite, включая разные даты и одновременные запросы.
- Сначала остановите таймер, затем исправляйте время вручную. Отметка «Выполнена»
  и закрытие дня также останавливают таймер.
- Менеджер меняет свои дополнительные задачи и фактические результаты. Условия
  задач руководителя защищены; после утверждения плана цель и плановое время
  меняются через запрос. Руководитель может редактировать их непосредственно.
- Запросы видны руководителю во вкладке «Запросы», менеджеру — под своим планом
  и результатами. Интерфейс обновляет данные каждые 30 секунд, при возврате в окно
  и по кнопке «Обновить». Отдельная Telegram-рассылка согласований на этапе 1 не добавлена.
- До принятия запроса действует прежняя цель. Повторное решение и утверждение
  устаревшего запроса после изменения исходного значения блокируются.
- «Из предыдущего дня» создаёт **новый** план по последнему существующему плану
  более раннего буднего дня (пн–пт). Праздничный календарь пока не подключён.
  Факт, комментарии и таймеры обнуляются; выполненные задачи снова становятся
  запланированными. Внешние и уже перенесённые задачи не копируются.
- Перенос внутренней незавершённой задачи сохраняет исходную запись со статусом
  «Перенесена» и её фактом. На новой дате создаётся связанное продолжение с нулевым
  фактом. Это не выполнение задачи. Защита условий руководителя сохраняется.
- При утверждении сохраняется исходный снимок плана. Любое создание и изменение
  задач, переносы, таймеры и согласования фиксируются с автором, временем,
  прежним и новым состоянием. Параллельное редактирование защищено `revision`.
- После закрытия день недоступен для редактирования всем ролям, ожидающие
  запросы отменяются. Отчёт хранится отдельным снимком и отдаётся из `/report`.
  SQLite-триггеры запрещают обновление/удаление снимков и журнала через обычный SQL.
  Это защита приложения, а не защита от владельца сервера, способного изменить саму БД.
- История показывает последние 366 планов, очередь согласований — последние
  500 запросов, сначала ожидающие. Для небольшого отдела этого достаточно на этап 1.

## Bitrix24

На этапе 1 нет новой сетевой синхронизации. Существующее распределение недозвонов
работает прежним Bitrix-клиентом. В `planner/integrations.py` оставлены интерфейсы
для звонков (в том числе >180 секунд), задач/сроков и сделок категорий 0 и 2.
Предусмотрены `work_done_today`, внешний статус и два отдельных исхода переноса:
`work_done_and_moved` и `deadline_only`. Ни один из них сам по себе не закрывает
внешнюю задачу. Тип `bitrix` предусмотрен в БД и UI, но не создаётся и не изменяется
через пользовательский API. Статистика не подменяется демонстрационными числами.

## Локальная проверка — Windows PowerShell

Нужны Python 3.12+ и Node.js 22.12+ (или 24 LTS), pnpm 11.25.0.
Команды ниже не запускают polling бота и не обращаются к Telegram/Bitrix.

```powershell
cd C:\Users\user\bitrix_missed_calls_bot
.\.venv\Scripts\python.exe -m pip install -r requirements.txt -r requirements-planner.txt
.\.venv\Scripts\python.exe -m unittest discover -s tests -v
cd miniapp
npm install --global pnpm@11.25.0
pnpm install --frozen-lockfile
pnpm run build
pnpm run dev
```

В среде Codex, где `npm`/`pnpm` нет в PATH, доступен bundled pnpm:
`C:\Users\user\.cache\codex-runtimes\codex-primary-runtime\dependencies\bin\fallback\pnpm.cmd`.

Открыть демонстрацию: `http://127.0.0.1:5173/preview.html`.
Верхняя плашка явно обозначает вымышленные данные и позволяет переключить роль.
Для тёмной темы добавьте `?theme=dark`, для руководителя — `?role=supervisor`.
Демонстрация позволяет смотреть разделы и формы; сохранение блокируется с
сообщением. Она не ходит в API и не имеет способа войти в production.
`preview.html` и её модуль не входят в собранный сайт и Docker-образ.

Реальный локальный API (если нужно проверить вход через Telegram/HTTPS):

```powershell
cd C:\Users\user\bitrix_missed_calls_bot
.\.venv\Scripts\python.exe -m uvicorn planner.api:create_app --factory --host 127.0.0.1 --port 8000 --no-access-log
```

Он прочитает существующий `.env`, создаст **отдельный** `planner.db` и прочитает
`access.db` без миграции/записи. Обычное открытие сайта без Telegram покажет
приглашение открыть бота, а API ответит 401. Не передавайте реальные initData в
командной строке, скриншотах или сообщениях.

### Сквозной браузерный тест с временными базами

После `pnpm run build`, в первом PowerShell из корня проекта:

```powershell
.\.venv\Scripts\python.exe -m tests.planner_browser_server
```

Во втором PowerShell:

```powershell
cd C:\Users\user\bitrix_missed_calls_bot\miniapp
$env:PLAYWRIGHT_CHANNEL='msedge'
node tests/ui.cjs
```

Если Edge не установлен, выполните `pnpm exec playwright install chromium` и
запускайте тест без переменной `PLAYWRIGHT_CHANNEL`. На Linux используйте
`pnpm exec playwright install --with-deps chromium`.

Тест использует **вымышленный** токен, но настоящую проверку HMAC, временные БД,
собранный production-интерфейс и localhost:8765. Проверяет создание задач,
восстановление таймера, работу обеих ролей, утверждение цели, перенос и закрытие
дня. Скриншоты — `test-artifacts/`. Перед повторным полным тестом перезапустите
тестовый сервер, чтобы получить чистую временную базу. Не публикуйте этот сервер.

## Подготовка к production на действующем VPS

Актуальная инструкция — [PLANNER_DEPLOY.md](PLANNER_DEPLOY.md). Она учитывает
подтверждённый путь `/opt/bitrix_missed_calls_bot/data/access.db`, UID/GID 10001,
отдельный Compose-проект `bitrix-workday-planner`, loopback-порт 18080 и существующий
Nginx. Запуск Mini App через Menu Button не требует обновления рабочего бота.

Миграция v1 → v2 заполняет только пустой Telegram ID Яны, не создаёт дублей и
не перезаписывает непустые данные. До обновления существующей базы нужна копия.
Средства `planner.backup` проверяют целостность/SHA256 и восстанавливают в новый
файл; `planner.ops` проверяет пути, роли и текущий доступ только для чтения.

На этом этапе нет синхронизации статистики/задач Bitrix24. Настройка DNS, выпуск
сертификата, production Docker-сборка и проверка в Telegram на VPS выполняются
после отдельного подтверждения владельца сервера.
