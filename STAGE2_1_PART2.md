## Поведение и совместимость

Менеджер подтверждает только свой draft. Сервер повторно проверяет активность
и роль в транзакции. approved_by содержит ссылку на сотрудника, approved_at —
время; immutable событие plan_confirmed дополнительно содержит Telegram ID
инициатора. initial_snapshot фиксирует первоначальный план с задачами.
Повтор подтверждения approved возвращает текущий план без новых событий и
перезаписи снимка/времени, включая план, ранее утверждённый руководителем.
Чужой план/роль руководителя на /confirm запрещены; closed отклоняется.
Руководитель сохраняет прежний /approve, доступ менеджеру на него запрещён.

После подтверждения доступны таймеры, факт, время, результаты и комментарии.
Для остальных защищённых целей сохраняются запросы/согласования; первоначальный
снимок не изменяется после согласованного изменения действующей цели.
Количество imported task не меняет ни менеджер, ни руководитель: PATCH,
goal_requests и старый pending-request не обходят защиту. Перенос запрещён;
копирование прошлого плана пропускает такие задачи и сохраняет остальные.
DELETE API задач отсутствует и не добавлен. Pydantic extra=forbid запрещает
смену kind, plan_id, locked и признака защиты из произвольных API payloads.

Новых миграций по сравнению с первой частью нет: схема остаётся 3.
Старые immutable отчёты и аудит не переписываются. Совместимость чтения задач
из тестовой схемы 1/2 сохранена. Новые поля API дополнительные.

## Проверки

Полный набор: 120 Python-тестов, успешно. Production React: tsc --noEmit и
Vite build, успешно. Тестируются собственный/чужой/закрытый план, отсутствие
авторизации, отключённый менеджер, роль руководителя, конкурентные и повторные
подтверждения, исходный снимок, факт/таймеры, согласование времени и обычной цели,
защита imported target от PATCH/переноса/копирования/DELETE/подмены полей и
утверждения старого запроса. Остальные регрессионные тесты бота также проходят.

## Ограничения

Изменение количества или перенос импортированной задачи в первом релизе
не предусмотрены. Нужно отдельное согласованное действие замены распределения.
Проверка не включает браузерный end-to-end тест новой кнопки, Docker или реальные
Telegram-клиенты. Production build проверяет TypeScript и комплект статических
файлов, а API-сценарии выполняются только на временных SQLite-базах.
Защита касается связанной импортированной задачи; пользователь по-прежнему
может добавить обычную количественную задачу, она не получает назначенных
лидов или статус распределения. Автоматической статистики обработки CRM нет.
