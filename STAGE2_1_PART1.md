# Этап 2.1: первая часть, локальная реализация

Реализованы очередь и атомарный импорт. Бот, API подтверждения менеджером,
интерфейс и автоматический цикл чтения очереди ещё не подключены.
Этот промежуточный код не предназначен для самостоятельного production-релиза.
Рабочие базы, сервер, Nginx и Docker-контейнеры не изменялись.

## Данные и права

`DistributionQueue.publish(snapshot, authorized_ids)` принимает отдельный явный
список полномочий. Роли manager/supervisor не предоставляют право автоматически.
В тестах уполномочен Вячеслав, руководитель проверяется отдельным разрешением.
Подключение списка к конфигурации бота будет следующим изменением.

Снимок содержит UUID, московскую дату, время подтверждения с часовым поясом,
инициатора, номер и ID варианта, версию формата, назначенные даты, сотрудников,
ID лидов, исходную стадию и количества. Разрешены только IN_PROCESS и проверенные
привязки Яны/Вячеслава. Телефоны, имена клиентов и CRM credentials не принимаются.
Уникальная дата очереди исключает второе распределение на день; одинаковый UUID
и SHA256 дают идемпотентный повтор. UPDATE/DELETE снимков запрещены триггерами.

## Импорт и восстановление

`import_once(store, queue, authorized_ids)` — явный локальный вызов.
Чтение очереди mode=ro/query_only, без создания отсутствующего файла.
Сначала чтение и закрытие очереди, затем отдельные транзакции BEGIN IMMEDIATE
планировщика. В одной транзакции сохраняются входящий снимок, назначения, лиды,
задачи и системная история. Любая ошибка SQLite откатывает всё распределение;
повторный вызов после устранения ошибки безопасен. Ошибка не помечается успехом.

Неактивный/непривязанный менеджер блокирует создание всех задач; сохраняется
снимок со статусом review. Неизвестный инициатор также требует рассмотрения.
approved/closed планы и отчёты не изменяются. Допустимые черновики могут получить
свои задачи, но распределение в целом имеет review, если хотя бы один план
требует рассмотрения. Повторный импорт review не превращает его в успех и не
пытается позднее сам менять планы. Отдельное рассмотрение будет будущим действием.

Системная история отдельная, неизменяемая. API истории возвращает actor_id=null,
actor_name=Система и after_json с реальным confirmed_by_telegram_id и confirmed_at.
Новые задачи имеют creation_actor=system. Старое обязательное поле created_by
сохраняет ссылку на инициатора исходного подтверждения, а не автора системного
действия; это явно разделено дополнительным полем и журналом. Старые записи
аудита не переписываются, фиктивный сотрудник-система не создаётся.

## Миграция

Версия planner.db 2 → 3: distributions, distribution_tasks, distribution_leads,
system_audit и tasks.creation_actor. Все изменения транзакционные. Существующие
сотрудники, задачи и immutable отчёты/аудит сохраняются. Backup API поддерживает
версии 1/2/3 и проверяет наличие новых таблиц для версии 3.
Store.initialize выполняет миграцию при вызове: **не вызывать на рабочей БД сейчас**.

## Предстоящая интеграция чтения и Docker (пока не включена)

Предлагаемая папка: /opt/bitrix_missed_calls_bot/distribution-queue, отдельная
от data и planner-data, UID:GID 10001:10001, каталог 700, файл 600.
Бот: отдельный RW bind; Mini App: RO bind всей папки, create_host_path=false.
Оба контейнера уже используют UID 10001. Очередь использует DELETE journal,
не WAL. Следует проверять чтение при живом writer, права каталога и отсутствие
hot journal; reader не получает права восстановления журналов. При аварийном
hot journal его восстанавливает writer перед чтением. Проверка реального bind
mount на Linux остаётся обязательной перед развёртыванием: Docker локально нет.

Следующим изменением предлагается один цикл импорта в lifespan FastAPI,
первое чтение при запуске, затем каждые 30 секунд. Сетевых CRM-запросов нет.
При временной ошибке цикл повторяет попытку с ограниченной задержкой; логи
содержат тип ошибки и технический ID, без payload/credentials. Ошибка одного
снимка не должна показываться как успех; административная готовность импорта
будет отдельна от HTTP healthcheck. Завершение процесса отменяет цикл корректно.
Сам цикл, конфигурация, интерфейс review и усиление правил редактирования/
копирования импортированных задач относятся к следующим частям.

## Проверка локально

```powershell
.\.venv\Scripts\python.exe -X utf8 -m unittest tests.test_distribution_import -v
.\.venv\Scripts\python.exe -X utf8 -m unittest discover -s tests
```

Все тесты работают с TemporaryDirectory. Тестируются повторы/конкуренция,
частичный сбой/откат/восстановление, draft/approved/closed, явные полномочия,
inactive, несовпадающие привязки/количества, дубли лидов, неподходящие стадии,
неизменяемость очереди, миграция и backup/restore.

Результат: полный набор 113 тестов успешно выполнен 13.10.2026; 12 новых
тестов посвящены очереди/импорту. Контрольные суммы рабочих .env, access.db,
bot.py, config.py, bitrix.py, distribution.py, compose.yaml, Dockerfile и
requirements.txt совпадают с исходными. React не менялся; сборка образа Docker
и Linux bind mounts здесь не выполнялись.

## Будущее развёртывание и откат

На этом подэтапе нет команд применения к VPS: подготовка общего релиза будет
после остальных частей и отдельного согласования обновления контейнеров.
Перед миграцией: проверенный SQLite backup planner.db, сохранённые старые образы
и каталоги, отдельный backup очереди через SQLite Backup API, не cp живой базы.
Сначала обновить Mini App с выключенным импортом, проверить миграцию, потом
подключить очередь и обновить только бот в согласованное окно. Основной Compose
не смешивать с проектом bitrix-workday-planner, не использовать общий down.
Nginx и Bitrix24 не меняются.

Откат версии 3 на 2 требует восстановления проверенной старой копии в новую
папку данных, старый backend новую схему отвергает. Не перезаписывать рабочий
planner.db, не восстанавливать access.db. Очередь и неудачную базу сохранить;
позднейшие записи требуют отдельного разбора. Повторный импорт очереди после
возвращения на этап 2.1 восстанавливает распределения идемпотентно.
