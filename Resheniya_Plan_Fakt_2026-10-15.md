# «План / факт» и @nedozvons_bot — зафиксированные решения

**Актуализация:** 15 октября 2026 года  
**Назначение:** основной документ решений для продолжения работы в проекте ChatGPT и при постановке задач Codex.  
**Статус:** согласованные требования; не является заявлением, что всё перечисленное реализовано.

> **Правило актуальности:** более позднее прямо подтверждённое решение имеет приоритет над старым предложением. Спорные и невыясненные вопросы не считать согласованными. Не включать планируемые функции в описание работающей версии.

## 1. Архитектура продукта и новое решение о веб-версии

**Утверждено 15.10.2026:** Telegram Mini App и полноценную веб-версию развивать **параллельно**, а не ждать полного завершения Mini App.

- **Веб-версия сразу для обеих ролей:** менеджеры (Вячеслав и Яна) **и руководитель**, без промежуточного релиза только для менеджеров. Реализовывать её по частям локально допустимо, но первую опубликованную рабочую версию проектировать для обеих ролей.
- **Веб-интерфейс полноценный и ориентированный на компьютер:** левое боковое меню, широкие таблицы, поиск, фильтры, подробные отчёты, рабочие страницы задач, планов и согласований. Это **не увеличенная копия Mini App**.
- **Mini App:** компактный мобильный Telegram-интерфейс для быстрых действий.
- **Единая система:** общие backend, бизнес-правила, API и база данных. Данные, статусы, фактическое время, таймеры и согласования должны совпадать в обоих интерфейсах; дубликаты недопустимы.
- **Вход:** Telegram initData для Mini App; логин/пароль и отдельная защищённая сессия для веб. Общая модель ролей и прав. Пароли не хранить в открытом виде.
- **Управление учётными записями:** руководитель создаёт сотрудников, назначает роли, отключает доступ и сбрасывает пароли.
- **Устройства:** работа в Windows (менеджеры) и macOS (руководитель) через обычный браузер. Отдельные устанавливаемые приложения пока не являются целью.
- **Подход к разработке:** новые функции проектировать сразу для обоих интерфейсов; бизнес-логику не дублировать. Не создавать две базы или независимые реализации таймеров.
- **Перед реализацией:** учесть результаты полного локального аудита Codex; решить, что можно переиспользовать из React, а что адаптировать под desktop.

### Предлагаемая структура desktop-интерфейса (детали дизайна ещё не утверждались)

Менеджер: «План дня», «Задачи», «История», «Мои отчёты».  
Руководитель: «Обзор отдела», «Планы менеджеров», «Согласования», «Отчёты», «Сотрудники».  
Предусмотреть табличную работу, выбор периода и сотрудника, разворачивание подпунктов, отображение план/факт. Точный дизайн — отдельное проектирование.

## 4. Версия 2.2: бот, стадии, обработка лидов

**Утверждены три стадии:**

1. «Недозвоны» — технический ID `IN_PROCESS` известен.
2. «Неудобно говорить» — технический ID ещё нужно установить.
3. «Не обработан» — технический ID ещё нужно установить.

**Утверждён порядок:** выбирать нужные стадии и подтверждать **одно общее распределение за день**. Распределение учитывает общую нагрузку менеджеров, но сохраняет исходную стадию, ID лида, дату, менеджера и количество **отдельно по каждой стадии**.

В Mini App показывать **«Назначено / Обработано / Осталось»** отдельно по стадиям и суммарно. Если лид изменил исходную стадию, он считается **обработанным по технической метрике CRM**, но **не автоматически состоявшимся разговором**. Никакого двойного импорта, потери исходного распределения и заднего изменения количества. Чтение Bitrix24 без записи.

*Открыто для технического ТЗ:* точные ID двух стадий, правила событий обработки/возвратов стадий, тестирование границ суток по московскому времени.

## 5. Типы и режимы задач (согласовано 14.10)

### 5.1. Типы

Сохранить существующие пользовательские варианты:
- **Обычная задача** — разовое действие, описание и результат.
- **Количественная задача** — плановая цель и фактическое количество.
- **Задача по клиенту** — действие, связанное с конкретным клиентом.

**Добавить отдельный понятный пользователю тип «Общая задача»** — контейнер с раскрывающимися подпунктами, например «Заявки», «Задачи Битрикс», «Обзвон действующих», «Обзвон завершённых». Не путать новый тип с существующим внутренним названием `general` в старом коде: техническую миграцию и отображение типов нужно спроектировать отдельно.

### 5.2. Подпункты общей задачи

Подпункт может содержать клиента, телефон (необязательно), действие, статус, результат, комментарий, фактическое время и ссылку/ID карточки Bitrix24 при наличии. Подпункты можно создавать вручную или выбирать клиента из Bitrix24. При выборе из CRM **сначала предлагать клиентов из задач менеджера на сегодня**, затем разрешать поиск среди других доступных контактов по имени/телефону.

Не импортировать автоматически всех клиентов CRM в дневной план. Подпункты не увеличивают число исходных задач: «Задачи Битрикс — 15» и четыре подробно расписанных клиента **не означают 19 задач**.

### 5.3. Независимый режим «В течение дня»

Применим к разным типам задач. **Плановое время может быть не задано** (это не то же, что `0 минут`), но может существовать количественная цель. Пример: «Обычные разговоры более 3 минут», цель 5, время заранее неизвестно. Не запускать один бесконечный девятичасовой таймер; учитывать фактическую работу частями.

## 6. План, изменения, согласования (согласовано 14.10)

**До подтверждения плана менеджером:** можно самостоятельно создавать/редактировать задачи, подпункты, цели и плановое время, включая автосформированные задачи; без лишнего согласования руководителя.

**После подтверждения** без согласования разрешены: добавление новых задач/подпунктов, увеличение количественной цели, уточнение описания, внесение факта и комментариев, завершение работы.

**Обязательно согласование руководителя:** изменение утверждённого планового времени, снижение утверждённой цели, удаление утверждённой задачи или подпункта. Сохранять причину, исходное и новое значение, автора, дату, решение и историю. До решения первоначальный утверждённый план не подменять.

**Открыто:** удаление вновь добавленных после подтверждения задач/подпунктов, отдельные спорные случаи редактирования.

## 7. Учёт времени и защита от дублей

Единая фактическая продолжительность работы; каждая минута учитывается **один раз**. Время родительской задачи и время её подпунктов нельзя безусловно складывать. Например, 90 минут всего по Bitrix24, из них 50 минут распределены по клиентам — итог **90**, не 140.

Таймеры и состояние работы должны совпадать в Telegram и веб-версии. Телефонная длительность — аналитический показатель **внутри рабочего времени**, а не дополнительные часы.

Точная модель атомарных записей времени, параллельных таймеров и распределения времени по подпунктам — на архитектурное проектирование.

## 8. Задачи Bitrix24 и переносы (последующие релизы)

Автоматически получать задачи менеджера на сегодня, формировать групповой показатель вроде «Задачи Битрикс — 15». Менеджер по желанию раскрывает конкретные задачи/клиентов, добавляет комментарии. Сохранять CRM ID и ссылку, не создавать повторных копий.

Разделять **«выполнена работа и перенесена»** и **«только изменён срок»**: простой перенос не доказывает фактическое выполнение. Считать просрочки и изменения без записи обратно в CRM.

**Открыто:** включать ли просроченные задачи и задачи без срока в показатель «на сегодня».

## 9. Обзвон действующих и завершённых клиентов «Сопровождения»

Отдел «Сопровождение» ведёт клиентов по процедуре списания долгов. Отдел продаж звонит, чтобы получить обратную связь и узнать о возможных рекомендациях знакомых, которым требуется списание долгов.

**Две отдельные дневные задачи:** «Обзвон действующих клиентов» и «Обзвон завершённых клиентов». Плановая цель каждой — **успешные разговоры с обратной связью**, не простые наборы номера. Не подгружать в план весь канбан.

**Отдельно считать попытки и успешные разговоры.** Три звонка одному клиенту — три попытки; ни одного ответа — ноль успешных. Реальный пример: **26 попыток / 4 успешных разговора**, по два с действующими и завершёнными. По успешным разговорам записывать имя клиента, телефон, краткую обратную связь и наличие рекомендаций.

Сохранять общий таймер Mini App на выполнение работы. По возможности автоматически получать длительность телефонных разговоров и попытки из телефонии, но без двойного учёта времени; источник пока не подтверждён.

**Существующая отдельная таблица учёта звонков не относится к дневному плану.** Не планировать её интеграцию или замену без нового отдельного решения.

**Открыто:** точные CRM-стадии канбана «Сопровождение» по категориям; источник автоматического подсчёта; правило повторных успешных разговоров с одним клиентом в день; критерий учёта звонков/обратной связи через мессенджеры.

## 10. Вечерние отчёты, аналитика, продажи

Вечерний отчёт «План / факт» должен учитывать первоначально подтверждённый план, добавленные в течение дня задачи, решения по согласованиям, фактическую работу, переносы, время без дублей, обработанные лиды, звонки и результаты по клиентам. Менеджер проверяет перед сдачей; руководитель видит отдел и сотрудников.

Позднее: дневная/недельная/месячная аналитика, консультации, качественные клиенты, договоры, ожидание оплаты и личный план продаж из воронки Bitrix24, если данные надёжно доступны только на чтение.

Дополнительные идеи, **не согласованные для ближайшего релиза**: напоминания, недельное планирование, предупреждения о перегрузке, расширенная история клиентов, поиск и офлайн-черновики.
