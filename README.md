# Распределение недозвонов

В этом же проекте добавлен первый этап Telegram Mini App «План дня»:
планы, серверные таймеры, согласования целей и отчёты. Локальный запуск,
проверки, роли и будущая настройка на VPS описаны в [PLANNER.md](PLANNER.md).
Для действующего VPS с Docker и существующим Nginx подготовлена отдельная
[инструкция установки, HTTPS, резервирования и отката](PLANNER_DEPLOY.md).
Mini App подключается отдельно; рабочие конфигурация Docker и база доступа бота сохранены.

Внутренний Telegram-бот получает лиды Bitrix24 в выбранных стадиях, считает их
по календарной дате создания и распределяет целые даты между 1–3 менеджерами
с оптимальным балансом количества лидов. Результат — инструкция в Telegram.
Бот не изменяет лиды, стадии или ответственных в Bitrix24.

Для постоянной работы на VPS через Docker Compose см. [пошаговый перенос с systemd](DOCKER.md).
В проект включены `Dockerfile`, `compose.yaml` и `.dockerignore`; база доступа хранится
на сервере отдельно от контейнера, в папке `data`.

## Требования и установка

Python 3.11 или новее, доступ к Telegram и к REST API вашего портала Bitrix24.
Нужен режим CRM с лидами и пользователь webhook с правом чтения нужных лидов.
Проверено на Python 3.14, aiogram 3.31 и httpx 0.28.

Все команды выполняются в текущей папке `bitrix_missed_calls_bot`.

Windows PowerShell:

```powershell
python -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install -r requirements.txt
```

Если `.venv` уже существует и работает, создавать его заново не нужно.
Если PowerShell блокирует активацию, можно вызывать интерпретатор напрямую:

```powershell
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\python.exe bot.py
```

Linux/macOS:

```bash
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
```

Зависимости: `aiogram`, `httpx`, `python-dotenv`, `tzdata`. Последняя нужна
для базы часовых поясов, в частности на Windows. Тесты используют стандартный
`unittest`, дополнительных библиотек для них не требуется.

## Конфигурация

Если `.env` ещё нет, создайте его из шаблона. Существующий заполненный `.env`
не перезаписывайте.

```powershell
Copy-Item .env.example .env
```

На Linux/macOS: `cp .env.example .env`.

Заполните следующие поля в `.env`:

| Параметр | Значение |
| --- | --- |
| `BOT_TOKEN` | Токен вашего бота из BotFather |
| `BITRIX_WEBHOOK_URL` | Полный базовый HTTPS-адрес входящего webhook, без имени REST-метода |
| `MISSED_CALL_STAGE_ID` | Код стадии лидов «Недозвоны», то есть `STATUS_ID` |
| `INCONVENIENT_STAGE_ID` | Код стадии «Неудобно говорить», для текущего портала `PROCESSED` |
| `UNPROCESSED_STAGE_ID` | Код стадии «Не обработан», для текущего портала `NEW` |
| `ALLOWED_TELEGRAM_IDS` | ID для начального заполнения SQLite, через запятую; допускается пустое значение |
| `ADMIN_TELEGRAM_IDS` | ID администраторов через запятую; имеют доступ независимо от SQLite |
| `MANAGER_1_NAME` | Имя первого менеджера |
| `MANAGER_2_NAME` | Имя второго менеджера |
| `MANAGER_3_NAME` | Имя третьего менеджера |
| `TIMEZONE` | `Europe/Moscow`; используется и при отсутствии переменной |
| `ACCESS_DB_PATH` | Необязательный путь SQLite; по умолчанию `access.db` рядом с исходниками, в Docker — `/data/access.db` |

Имена должны быть разными, до 64 символов, без переносов строк. Имена менеджеров
служат подписями результата, это не ID сотрудников Bitrix24 или Telegram.
Имя «Женя» при загрузке заменяется на «Евгений», чтобы обновление работало и со старым
серверным `.env`. В настройках также можно сразу указать полное имя.
Новые стадии необязательны: без соответствующего ID кнопка помечена как ненастроенная
и не включается в расчёт. Нельзя продолжить без хотя бы одной выбранной стадии.
Для московских расчётов оставьте `TIMEZONE=Europe/Moscow`.
Переменные окружения процесса имеют приоритет над `.env`.
Импорт модулей и тесты работают без секретов; запуск бота проверяет все обязательные
параметры и при ошибке завершается с понятным сообщением без их значений.
Без `ADMIN_TELEGRAM_IDS` бот продолжает обслуживать разрешённых пользователей,
но команды управления доступом недоступны. Если оба списка пусты и база новая,
доступа не будет ни у кого. Для настройки достаточно указать администратора;
остальных пользователей он сможет добавить командами.

## Telegram: BotFather и ID пользователей

1. Откройте официальный [BotFather](https://t.me/BotFather), отправьте `/newbot`.
2. Задайте отображаемое имя и уникальный username по подсказкам BotFather.
3. Запишите выданный токен только в `BOT_TOKEN` внутри `.env`.
4. Пользователи должны открыть созданного бота и отправить ему `/start`.
5. Числовой ID можно получить через `getUpdates` своего бота до запуска polling,
   без передачи данных сторонним ботам. После заполнения `BOT_TOKEN` откройте
   `python` в активированном окружении и выполните:

```python
import asyncio
import os
from aiogram import Bot
from dotenv import load_dotenv

load_dotenv(".env")

async def show_user_ids():
    try:
        async with Bot(os.environ["BOT_TOKEN"]) as bot:
            updates = await bot.get_updates(timeout=0)
            for update in updates:
                if update.message and update.message.from_user:
                    user = update.message.from_user
                    print(user.id, user.first_name)
    except Exception:
        print("Не удалось получить ID. Проверьте токен и остановите работающий бот.")

asyncio.run(show_user_ids())
```

Сопоставьте пользователей с их ID и внесите нужные числа в `ALLOWED_TELEGRAM_IDS`.
Не используйте username или ID бота вместо ID человека. Если список пуст,
попросите пользователя отправить новое сообщение и повторите команду.
Во время этого шага основной бот должен быть остановлен; для него не должен
быть настроен Telegram webhook от другой интеграции.

Официальные инструкции: [создание бота](https://core.telegram.org/bots/tutorial),
[getUpdates](https://core.telegram.org/bots/api#getupdates).

## Bitrix24: webhook и стадия

1. В Bitrix24 откройте раздел для разработчиков / локальных интеграций и создайте
   **входящий webhook** с доступом к CRM (`crm`). Названия разделов зависят от интерфейса портала.
2. Webhook работает от имени создавшего его сотрудника. У сотрудника должен быть
   доступ на чтение всех лидов, которые требуется учитывать. Лиды вне его прав
   не попадут в расчёт. По возможности используйте сотрудника с правами только чтения.
3. Скопируйте базовый URL вида `https://ваш-портал/rest/ID/секретный-ключ/`
   в `BITRIX_WEBHOOK_URL`. Не добавляйте `crm.item.list.json` к значению настройки.
4. В конструкторе запросов webhook выберите метод чтения `crm.status.list` и фильтр
   `ENTITY_ID=STATUS`. Найдите строку с `NAME`, равным названию вашей стадии «Недозвоны».
5. Значение **`STATUS_ID`** этой строки запишите в `MISSED_CALL_STAGE_ID`.
   Поле `ID` записи справочника для этой настройки не подходит. Не придумывайте код
   стадии: он зависит от вашего портала.

Документация: [входящие webhook](https://apidocs.bitrix24.com/local-integrations/local-webhooks.html),
[справочники CRM](https://apidocs.bitrix24.com/api-reference/crm/status/crm-status-list.html).

## Запуск и использование

```bash
python bot.py
```

Оставьте процесс работающим; для остановки нажмите `Ctrl+C`.
Откройте личный чат с ботом и отправьте `/start`:

1. Нажмите «📊 Распределить недозвоны».
2. Отметьте от одного до трёх менеджеров. Изначально выбраны все трое.
3. Выберите стадии: «Недозвоны», «Неудобно говорить», «Не обработан» — отдельно или вместе.
4. Выберите 3, 4, 5, 6, 7, 10 или 15 дней.
5. При наличии пустых дат добавьте замены или продолжите без них.
6. Получите распределение. «🔀 Другой результат» показывает следующий сохранённый
   вариант, «🔄 Новое распределение» полностью сбрасывает сценарий.

Бот работает в личных чатах, группах и супергруппах. Проверка доступа по ID человека
действует на сообщения и inline-кнопки; добавлять ID группы в список пользователей не нужно.
Для остальных пользователей ответ: «У вас нет доступа к этому боту.»
Старые кнопки и повторные одновременно пришедшие нажатия не выполняют действие заново.

## Работа в группе

Добавьте бота в группу и отправьте `/start@имя_бота`. Если Telegram не позволяет
добавить бота, разрешите добавление в группы в настройках BotFather.
Дайте боту право отправлять сообщения. Отключать Privacy Mode не требуется:
для запуска используйте адресованную боту команду, для ручного ввода даты — ответ
на специальное сообщение бота. Это соответствует механизму
[ForceReply и Privacy Mode](https://core.telegram.org/bots/api#forcereply).

Каждый пользователь с доступом ведёт собственный сценарий в каждом чате и теме.
Кнопки принадлежат пользователю, начавшему распределение. Другой участник должен
отправить свой `/start`; чужие кнопки не изменят результат. Обычную переписку бот
игнорирует. Анонимные сообщения от имени группы не запускают сценарий: для проверки
доступа необходим личный Telegram ID.

Результаты в группе видны её участникам. Команды `/adduser`, `/removeuser`, `/users`
остаются доступны только администраторам бота и только в личном чате.

## Ежедневное напоминание

В 10:00 по `Europe/Moscow` бот предлагает распределить «Недозвоны» и показывает кнопку
начала сценария. Напоминание не читает Bitrix24 и не запускает расчёт автоматически.

- В личных чатах напоминания автоматически включаются пользователям с доступом,
  включая администраторов. Пользователь должен хотя бы раз начать личный чат с ботом;
  Telegram не позволяет боту первым открыть такой диалог.
- Для выбранной группы администратор из `ADMIN_TELEGRAM_IDS` отправляет
  `/reminders_on@имя_бота`. В группе с темами напоминание приходит в ту тему, где
  выполнена команда. Можно включить напоминания в нескольких группах/темах.
- `/reminders_off` отключает напоминания в текущем чате/теме. В личном чате каждый
  пользователь управляет своей подпиской; в группе — администратор бота.
  Повторный `/start`, импорт пользователей и перезапуск сохраняют отключение.
- Общую кнопку напоминания может нажать любой пользователь с доступом: для него
  создаётся новое отдельное меню с «Недозвонами», выбранными по умолчанию.

Планировщик работает внутри процесса бота, без cron и дополнительных сервисов.
Подписки и отметки отправки хранятся в той же SQLite. Проверка времени выполняется
каждые 30 секунд; если процесс запустился между 10:00 и 10:10, напоминание ещё будет
отправлено. Позже пропущенное напоминание не догоняется. Отметка ставится до отправки:
перезапуск не создаёт повторов, но при сбое сети или процесса в момент отправки
напоминание за этот день может быть пропущено. Удалённые из доступа пользователи
не получают следующие напоминания. Подписка группы действует, пока включивший её
пользователь остаётся администратором бота.

## Управление доступом

Администраторов задавайте в `.env` через `ADMIN_TELEGRAM_IDS`: один положительный
Telegram ID или несколько через запятую. После изменения `.env` и после обновления
кода перезапустите `bot.py`. Программа не редактирует `.env`.

При каждом запуске рядом с `access.py` создаётся или открывается `access.db`,
создаётся таблица `allowed_users` и в неё добавляются отсутствующие ID из
`ALLOWED_TELEGRAM_IDS`. Повторный импорт не создаёт дубликатов и не перезаписывает
дату добавления или автора существующей записи. Импортированные записи имеют
`added_by=NULL`; при добавлении командой сохраняется ID администратора.

После импорта доступ ко всем сообщениям и кнопкам проверяется по правилу:
пользователь указан в `ADMIN_TELEGRAM_IDS` **или** присутствует в SQLite.
Проверка выполняется для каждого действия, без кеширования списка доступа.

В личном чате администратору доступны:

```text
/adduser 123456789
/removeuser 123456789
/users
```

- `/adduser` добавляет ID в базу; повторное добавление сообщает, что доступ уже есть.
- `/removeuser` удаляет ID из базы; отсутствующий ID обрабатывается без ошибки.
  Удалить себя или другого администратора этой командой нельзя: администраторы
  управляются только через `.env`.
- `/users` выводит отсортированное объединение пользователей базы и администраторов,
  отмечает администраторов и показывает итоговое количество. Дубликатов нет;
  длинный список отправляется несколькими сообщениями.

Обычный пользователь при попытке выполнить эти команды получает:
«⛔ Эта команда доступна только администратору.» Команды доступны администраторам
на любом шаге распределения и не сбрасывают текущий сценарий. Успешное добавление
или удаление записывается в лог с ID администратора и пользователя.

Изменения доступа командами действуют сразу для последующих действий и сохраняются
после перезапуска. Уже начавшийся запрос не отменяется при удалении пользователя.
**Исключение: ID, оставшийся в `ALLOWED_TELEGRAM_IDS`, будет снова импортирован
при следующем запуске.** Для окончательного удаления такого пользователя удалите
его ID и из этой переменной вручную. После первого успешного импорта можно очистить
`ALLOWED_TELEGRAM_IDS` и в дальнейшем управлять обычными пользователями через команды.

База содержит список доступа и подписки на напоминания: ID чатов/тем, включившего
пользователя и отметку последней попытки отправки. Для пользователей хранятся также
дата добавления в UTC и ID добавившего администратора.
Токены и webhook в ней не сохраняются. Файл базы и служебные файлы SQLite исключены
из Git. Для сохранения списка при переносе проекта перенесите `access.db` при
остановленном боте. При ошибке SQLite доступ обычным пользователям не предоставляется
по запасному списку из `.env`; бот показывает понятное сообщение об ошибке.

## Даты и пустые дни

Сегодняшний день никогда не учитывается, отсчёт начинается со вчерашнего.
Например, 21 сентября период «3 дня» означает 18–20 сентября.
Даты определяются динамически по `Europe/Moscow`, включая переходы месяца и года.
Лиды группируются по `createdTime` — дате создания в универсальном API, аналогу
`DATE_CREATE`. Дата переводится в настроенный часовой пояс перед группировкой.
Учитывается текущая стадия лида на момент запроса, а не история его переходов.
При выборе нескольких стадий запрос получает их объединение. Нагрузкой дня является
сумма лидов выбранных стадий за эту дату; вся сумма назначается одному менеджеру.
В итоговом списке при выборе нескольких стадий каждая дата показывает разбивку,
включая нули: `25.09.2026 — недозвоны 3, неудобно говорить 0, не обработан 6`.
Выводятся только выбранные стадии. Разбивка сохраняется для заменённых дат и
других вариантов распределения. При одной стадии остаётся прежний краткий формат.
Проверка ручной замены и поиск предыдущего дня используют те же выбранные стадии.

Дата с нулём лидов исключается. При нескольких пустых датах замены добавляются
по одной, пока не набрано выбранное количество непустых дат, максимум пятнадцать.

- «➕ Добавить предыдущий день» ищет ближайшую непустую дату раньше начала исходного
  периода, затем раньше последней автоматически найденной даты. Уже выбранные даты
  пропускаются. Поиск сортирует более ранние лиды по дате создания и затем считает
  весь найденный день, поэтому длинные пустые интервалы не требуют запроса на каждый день.
  Если более ранних лидов нет, бот сообщает об этом и оставляет другие варианты действий.
- «📅 Выбрать другую дату» принимает `15.09.2026` или `15.09`. Во втором случае
  используется текущий год в настроенном часовом поясе. Для предыдущего года укажите
  его явно. Сегодняшние, будущие и уже добавленные даты не принимаются. Нулевая дата
  не добавляется; можно ввести другую или вернуться к кнопкам.
- «Продолжить без замены» распределяет только непустые даты. Если их нет вообще,
  бот сообщает об этом и предлагает новое распределение.

После замены период результата может расшириться и иметь пропуски. В расчёте участвуют
только даты, явно перечисленные у менеджеров. Если непустых дат меньше, чем менеджеров,
у некоторых будет нулевая нагрузка.

## Алгоритм и альтернативы

Одна дата целиком принадлежит одному менеджеру. Точный алгоритм перебора с отсечением
ветвей работает для максимум 15 дат и 3 менеджеров. Вместо хранения и сортировки
`3^15` назначений он перебирает разбиения без перестановок имён, отбрасывает ветви,
которые уже не могут улучшить баланс, и хранит до шести оптимальных вариантов.
Оптимальность сохраняется; вычисление выполняется вне основного цикла обработки
сообщений. Варианты сравниваются по:

1. Разнице максимальной и минимальной нагрузки.
2. Сумме квадратов отклонений от средней нагрузки.
3. Стандартному отклонению.
4. Стабильному порядку дат и менеджеров.

При фиксированном количестве менеджеров критерии 2 и 3 математически эквивалентны.
Для сравнения используется целочисленный числитель суммы квадратов, без ошибок
округления; стандартное отклонение также доступно в структуре результата.

Сохраняется до шести вариантов **с теми же оптимальными значениями критериев**.
Сначала выбираются разные разбиения дат на группы независимо от имён. Если остаётся
место, добавляется одна циклическая перестановка менеджеров первого варианта.
Это даёт возможность сменить владельцев дат без десятков одинаковых разбиений.
Ухудшенные варианты не показываются. Повторов и циклического возврата к первому
результату нет. При исчерпании списка: «Других сопоставимых вариантов распределения
не найдено.» Для одного менеджера доступен только один результат.

## Архитектура и ограничения

- `config.py` — загрузка `.env`, валидация, часовой пояс и неизменяемая конфигурация.
- `access.py` — локальный список доступа SQLite, импорт, добавление, удаление и проверка ID.
- `distribution.py` — чистые функции работы с датами и полного перебора, dataclass-результаты.
- `bitrix.py` — async HTTP, пагинация, группировка и поиск предыдущей непустой даты.
- `keyboards.py` — небольшие функции inline-клавиатур.
- `bot.py` — aiogram Dispatcher, проверка доступа, FSM, тексты и обработка ошибок.
- `reminders.py` — ежедневные предложения распределения, московское время и защита от повторов.
- `tests/` — тесты расчётов, конфигурации, HTTP-клиента и Telegram-сценариев.

В рабочем клиенте Bitrix24 используется только метод чтения
[`crm.item.list`](https://apidocs.bitrix24.com/api-reference/crm/universal/crm-item-list.html)
с `entityTypeId=1`, фильтром стадии, полями `id`, `createdTime` и `stageId`.
HTTP POST здесь передаёт параметры запроса чтения, а не изменяет CRM.
Все страницы загружаются по `next`; последовательные даты запрашиваются одним диапазоном,
без запроса на каждый лид. Отсутствие лидов отличается от ошибки API. Ошибки формата,
авторизации, HTTP и timeout приводят к понятному сообщению и возможности повторить действие.

Состояние каждого пользователя хранится в `FSMContext` через `MemoryStorage`.
Перезапуск процесса очищает сценарии. Запускайте один экземпляр бота; постоянной
истории распределений нет. SQLite хранит список доступа и подписки на напоминания. Операции стандартного
`sqlite3` выполняются через `asyncio.to_thread`, с отдельным закрываемым соединением
на операцию, параметризованными запросами и транзакциями для записи.
«Другой результат» использует тот же снимок данных без повторного запроса.
Для свежих данных начните новое распределение. При изменениях CRM во время пагинации
API не гарантирует атомарный снимок; повторный расчёт может дать другие количества.

`.env` исключён из Git. Реальных секретов в исходниках и шаблоне нет. Ошибки логируются
без тел запросов, ответов и URL webhook; вывод логов дополнительно маскирует секреты.
Не добавляйте `.env` через `git add -f` и не публикуйте токены или webhook.

## Проверка без реальных секретов

Для полного набора тестов, включая Mini App, установите дополнительные зависимости:
`python -m pip install -r requirements.txt -r requirements-planner.txt`.

```bash
python -m unittest discover -s tests -v
python -m compileall -q bot.py config.py access.py bitrix.py distribution.py keyboards.py reminders.py planner tests
python -c "import config, access, distribution, bitrix, keyboards, reminders, bot; print('Imports OK')"
python -m pip check
```

Тесты не обращаются к настоящим Telegram или Bitrix24: используются `httpx.MockTransport`
и тестовая Telegram-сессия. Покрыты все запрошенные случаи распределения, московская
полночь, пустые даты и замены, ошибки API, несколько страниц, авторизация,
старые/повторные кнопки, независимые сессии и сброс сценария.
Тесты доступа используют только временные базы: рабочий `access.db` не открывается.
Проверяются первоначальный и повторный импорт, сохранение пользователей, повторное
и конкурентное добавление, удаление, права администратора, защита административных
команд, отзыв доступа для сообщений и кнопок, ошибки SQLite и длинный список пользователей.
Добавлены проверки периодов 10/15, точности оптимизации, объединения стадий,
групповых кнопок и тем, ручной даты в Privacy Mode и сохранения напоминаний после перезапуска.

Для первого реального запуска понадобятся токен BotFather, URL входящего webhook,
`STATUS_ID` стадии «Недозвоны», Telegram ID администратора/допущенных пользователей
и три имени менеджеров.
