# Этап 2.1 — третья часть: подтверждение в боте

Локальная разработка на Windows, 13.10.2026. Серверные действия не выполнялись.

## Изменения

- bot.py: кнопка в текущем меню, handler подтверждения, повторное чтение лидов
  каждой назначенной даты, UUID выбранного варианта, идемпотентность и сообщения.
- keyboards.py: необязательный параметр can_confirm, прежние кнопки сохранены.
- config.py: отдельные явные полномочия, путь очереди, привязки manager slots и
  список действующих менеджеров для передачи.
- .env.example: пустые параметры (отключено по умолчанию), рабочий .env не менялся.
- planner/distribution_queue.py: read-only поиск подтверждения по UUID варианта.
- tests/test_bot_confirmation.py: 9 новых тестов; tests/test_config.py: 1 новый.

## Поведение

Кнопка показывается только при единственной выбранной стадии IN_PROCESS,
настроенном пути очереди и явном разрешении пользователю. Роль администратора,
manager/supervisor и обычный доступ к боту не предоставляют право автоматически.
Чтобы дать право Вячеславу, необходимо отдельно указать его Telegram ID
в DISTRIBUTION_CONFIRMER_IDS. Руководитель добавляется отдельно после решения.
На подделанный callback сервер повторно проверяет полномочия и стадию.

Каждый расчёт имеет session UUID; каждый variant_index — стабильный отдельный
UUID. «Другой результат» только меняет меню, ничего не публикует. Сохраняется
текущий показанный вариант. Callback middleware сохраняет проверку владельца,
ревизии и message_id; SimpleEventIsolation сериализует нажатия одного сценария.
SQLite unique workday защищает также параллельные сценарии разных пользователей.

В момент подтверждения get_leads вызывается на каждой назначенной дате с
stage_ids=(IN_PROCESS,). Проверяются количество по каждой дате, стадия, дата
создания по Москве, уникальность ID и назначенных дат. Другие стадии не передаются.
Сохраняется только целиком проверенный снимок. Время/рабочий день фиксируются по
Москве после получения лидов. CRM только читается, ответственные не меняются.

Повтор того же callback сначала читает уже сохранённый UUID и возвращает
существующий итог без новой проверки CRM/записи. Это восстанавливает ответ после
сбоя между commit и уведомлением Telegram. Другой вариант в тот же день получает
отказ. Потеря FSM при рестарте делает старую кнопку устаревшей; постоянная очередь
остаётся, новое подтверждение на тот же день не заменит прежнее.

Итог содержит дату, номер варианта, менеджеров, назначенные даты и количества.
Он сообщает именно сохранение в очередь, а не успешный импорт в Mini App.
При изменившихся данных/BitrixError/ошибке SQLite меню сохраняется для повторения
или «Новое распределение». Секреты и payload в новые логи не выводятся.

## Настройки для будущего релиза (сейчас не применять на VPS)

```dotenv
DISTRIBUTION_QUEUE_PATH=/distribution-queue/confirmations.db
DISTRIBUTION_CONFIRMER_IDS=8306778724
PLANNER_ACTIVE_MANAGER_IDS=8306778724,7939114214
```

MANAGER_1/2/3_TELEGRAM_ID заполняются по реальному порядку MANAGER_N_NAME.
Не предполагать, что первая строка всегда Вячеслав. Для Евгения ID оставить
пустым: его имя/слот в старом боте сохраняются, но вариант с ним не передаётся.
Пустые параметры не влияют на прежнее распределение. Повторяющиеся/невалидные
Telegram ID конфигурация отклоняет безопасным сообщением.

## Ограничения и следующая часть

Список активных сотрудников на стороне бота пока явно конфигурационный.
Изменение active через Mini App не передаётся боту в реальном времени: это
потребует согласованного обмена состоянием в следующей интеграции. Импорт первой
части независимо проверяет активность в planner.db и при отключённом сотруднике
блокирует создание всех задач. Сейчас нельзя заявлять о live-проверке active
перед подтверждением. Нет прямого чтения planner.db процессом бота.

Чтение CRM по отдельным датам не является общей транзакцией Bitrix24: позднейшие
изменения стадий возможны. При неизменившемся количестве сохраняется актуальный
состав ID на момент проверки; первоначальные ID при расчёте не запрашиваются.

Автоматический reader Mini App, Docker mounts и упаковка нового образа бота
не подключены: это четвёртая часть. Старый bot Dockerfile не включает новый
planner.distribution_queue; для будущего релиза потребуется явно включить этот
stdlib-модуль и planner/__init__.py, без запуска API или второго polling.
Этот промежуточный код не развёртывать существующим Dockerfile.

## Проверки

Полный набор: 130 Python-тестов успешно. 10 новых тестов проверяют выбранный
вариант, явные права, устаревший callback, неподходящие/смешанные стадии,
неактивный слот, изменение количества, дубли ID, BitrixError, сбой очереди до/
после commit, параллельные/повторные запросы и конфликт вариантов одного дня.
Все CRM ответы имитируются, базы временные. Frontend этой частью не изменялся.
Реальные Telegram-клиенты, VPS, Docker bind mounts и CRM не проверялись.

Рабочие .env/access.db, Dockerfile/Compose, bitrix.py и distribution.py не
изменялись. bot.py и config.py изменены только локально; действующий контейнер
не обновлялся и не перезапускался. Nginx и данные Bitrix24 не затронуты.
