# Исходники и безопасная работа с Git

Репозиторий: https://github.com/emerald634/planer (Private).
Первый импорт фиксирует локальный срез на 21.10.2026, включая кандидат 2.1.1.
Это не восстановленный исходный релиз 2.1 и не подтверждение установки 2.1.1.
Production не обновляется при отправке исходников в GitHub.

## Восстановление окружения

После клонирования нужны Python 3.11+ (Docker использует 3.12), Node.js,
совместимый с Vite из lockfile, и pnpm. Секреты для чтения исходников и тестов
не нужны. Зависимости устанавливают отдельно, не копируют из старой `.venv`
или `node_modules`:

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt -r requirements-planner.txt
.\.venv\Scripts\python.exe -B -m unittest discover -s tests
Set-Location miniapp
pnpm install --frozen-lockfile
pnpm run build
node tests/hotfix-api.cjs
```

Версии frontend зафиксированы в `miniapp/pnpm-lock.yaml`; ограничения backend —
в `requirements-planner.lock.txt`. Зависимости бота пока заданы диапазонами:
полной фиксации Python-окружения этот импорт не добавляет.
Браузерные сценарии и изолированный сервер описаны в `PLANNER.md`,
`HOTFIX_2_1_1.md` и `HOTFIX_2_1_1_AUDIT_FIXES.md`.

Для настоящего запуска создают отдельные конфигурации из `.env.example` и
`deploy/planner.env.example`. Не перезаписывают имеющиеся настройки. Токены,
initData, клиентские сведения, базы и их копии в Git не добавляют.

## Сборка и развёртывание

**Корневые `Dockerfile`, `compose.yaml` и `DOCKER.md` исторические; обнаружено
отсутствие модуля очереди в старом образе бота (A04). Не использовать этот
сценарий как готовую инструкцию для текущего кода.**

Актуальное разделение компонентов описано в `STAGE2_1_RELEASE.md`:
`deploy/Bot.Dockerfile` с `compose.bot.release.yaml` и
`deploy/Planner.Dockerfile` с `compose.planner.yaml`.
Для Mini App сначала требуется локальная production-сборка и упаковка через
`deploy/package_release.py`: архив включает `miniapp/dist` и манифесты,
которых намеренно нет в Git. Один checkout не является готовым Docker-релизом.
Исторические имена релиза в упаковщике не изменены; для следующего выпуска
нужна отдельная согласованная подготовка нового имени, метаданных и архива.

Установка на VPS, миграции, работа с настоящими базами и перезапуск сервисов —
только после отдельного разрешения. В репозиторий не добавляется автоматический
деплой. Git не заменяет резервирование SQLite и проверку отката.

## Порядок изменений

- `main` — принятый срез исходников.
- Каждая задача — отдельная ветка, например `fix/a03-importer` или `feature/...`.
- Перед объединением: просмотр diff, проверка секретов и подходящие тесты.
- Перед отправкой: `git status`, `git diff --cached --stat` и просмотр staged diff.
  Не применять `git add -f` к исключённым данным.
- После принятия изменений обновлять `PROJECT_MASTER_KNOWLEDGE.md`, сохраняя
  различие между локальным кандидатом и установленным релизом.
- Для будущего релиза записывать commit SHA, схему данных, контрольные суммы
  артефактов и фактические результаты проверок. Старые исторические теги не
  восстанавливать предположительно.
- Копия главной базы знаний в ChatGPT обновляется отдельно владельцем.

Наличие Git улучшает будущую прослеживаемость A20, но не восстанавливает
утраченные исходные срезы прошлых выпусков. Правила `.gitignore` уменьшают A23,
но не предотвращают намеренное добавление секретов или их появление в тексте.
