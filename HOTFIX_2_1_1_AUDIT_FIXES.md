## A02 — контекст операции и загрузки

Файл: `miniapp/src/App.tsx`, состояния плана, `refresh`, эффект смены контекста,
`act`.

Ранее `act` после сохранения вызывал `refresh`, замкнувший старые дату и сотрудника.
Этот старый вызов получал уже новый номер поколения и мог записать старый план
в состояние нового экрана.

Внесены изменения:

- У контекста даты и сотрудника появилась идентичность, которая меняется и при
  переходе туда-обратно. Каждый загрузчик проверяет её вместе с поколением и
  номером запроса. Устаревший `refresh` не начинает загрузку.
- Перед отправкой изменения фиксируются контекст и ID выбранного плана.
  После ответа проверяется их актуальность. Старый callback не закрывает диалог
  другого контекста и не записывает туда ошибку исходной операции.
- После успешного сохранения вызывается актуальный `refresh` через ref.
  Ответ операции не вставляется напрямую в отображаемый план. Результат остаётся
  в исходном плане на сервере и загружается при возвращении к нему.
- При смене контекста успешное действие сопровождается сообщением, что оно
  относится к ранее выбранному плану.
- Отображение плана дополнительно ограничено совпадением его даты и сотрудника
  с выбранными значениями: предыдущий план не отображается даже до очистки
  состояния эффектом React.
- Ответ detail/report проверяется на совпадение ID, даты и сотрудника с
  запрошенным планом. Структурно корректный чужой ответ становится ошибкой
  раздела «Планы».
- При навигации очищаются старый диалог и история. Переходы даты и сотрудника
  не блокируются. Новых циклов обновления и зависимостей эффектов от самого
  плана не добавлено.

### Воспроизведение и проверка

До пересборки новый браузерный набор запускался против прежнего локального
`miniapp/dist` 2.1.1. Во время задержанного сохранения тест переключал дату
или сотрудника и затем отпускал ответ. После завершения старой операции вместо
задачи нового контекста снова появлялась задача исходного плана.

Воспроизводились запуск и остановка таймера, изменение и создание задачи,
подтверждение плана, создание запроса согласования и решение руководителя.

После исправления проходят:

- Запуск/остановка таймера менеджером и переход на другой день.
- Изменение/создание задачи с переключением дня либо сотрудника руководителем.
- Подтверждение собственного плана с переключением дня.
- Отправка запроса изменения цели/времени с переключением дня.
- Решение по согласованию с переключением дня либо сотрудника.
- Утверждение руководителем и переход к другому сотруднику и обратно до ответа.
- Возвращение в исходный план: сохранённый результат остаётся именно в нём.
- Один запрос изменения без автоматического повтора; ограниченное число
  загрузок без цикла React.
- Отказ от отображения корректного по структуре detail другого плана.

Таймеры и подтверждение собственного плана недоступны руководителю по правилам
приложения; для них проверялось переключение даты менеджером, а для смены
сотрудника — доступные руководителю операции.

Браузерные тесты с редактированием/созданием задачи закрывают native dialog
программно после отправки, чтобы проверить смену контекста даже при незавершённом
ответе. Тест не добавляет такую кнопку в продукт. Обычные сценарии диалогов
дополнительно проходят через прежний интеграционный набор.

## A09 — runtime-проверки данных API

Файл: `miniapp/src/response.ts`; отображение исторической цели в
`miniapp/src/App.tsx`.

Добавлены либо уточнены проверки всех дополнительных полей, используемых
текущими JSX и обработчиками:

- `/me`: `workday.start/end` имеют формат реального времени `HH:MM`, timezone
  является строкой, reminders_enabled — boolean; проверяется также тип
  `crm.connected`, если поле присутствует.
- Сотрудники: необязательные `telegram_id` и `bitrix_id` — числа либо `null`.
- Задачи: `external_url`, `moved_to`, `elapsed_seconds`,
  `distribution_target_locked` и вложенный `distribution_source`.
- Внешняя ссылка должна быть корректным абсолютным HTTP(S) URL без логина и
  пароля. `javascript:`, `data:`, объекты и некорректные строки отклоняются.
  Корректный старый HTTP URL не блокирует план, но интерфейс, как прежде,
  показывает ссылку только при `https://`.
- Сводки планов сохраняют числовые проверки всех отображаемых показателей.
- Запросы согласования: при наличии проверяются created_at/decided_at.
- Уведомления: проверяется необязательный employee_id.
- Закрытые отчёты используют те же проверки, что и детали плана.
- Для `initial_snapshot.tasks` проверяются именно отображаемые исторические
  поля: id, title, planned_minutes и необязательный target. Отсутствие новых
  полей задачи в старом снимке не является ошибкой.

Отсутствие необязательных полей допускается. В безопасных для текущего UI местах
допускается `null`: внешняя ссылка, IDs, workday, initial_snapshot,
distribution_source, даты решений и числовые значения, предусмотренные API.
Отсутствующая историческая цель не выводится как `undefined`.

Проверки обязательных текстов/чисел/массивов и объектов истории сохранены.
Произвольные значения внутри before_json/after_json допустимы: интерфейс истории
преобразует их в строки, а не вставляет объекты в JSX.

Невалидные ответы отклоняются до записи в состояние React. План, отчёт, сотрудники,
история, согласования и уведомления используют существующие сообщения ошибки
своего ресурса и повтор только этого ресурса. Ошибка `/me` выводится на начальном
экране с повторным открытием приложения, поскольку без корректного пользователя
нельзя безопасно показать рабочий интерфейс.

Дополнительный ErrorBoundary не понадобился для согласованных дефектов: граница
проверки данных устраняет воспроизведённые причины падения и оставляет штатные
ошибки/повтор загрузки. Это не обещание защиты от любых будущих ошибок React:
новые используемые поля должны сопровождаться соответствующей проверкой.

## A10 — история текущего плана

Файл: `miniapp/src/App.tsx`, загрузчик истории и эффект смены контекста.

- У запроса истории фиксируется ID плана. Результат и ошибка применяются только
  при совпадении этого ID с актуальным выбранным планом, контекста и версии
  запроса.
- При смене дня/сотрудника очищаются история, её ошибка и признак показа,
  инвалидируется версия старого запроса.
- При применении detail либо результата «плана нет» прежняя история и её ошибка
  также сбрасываются. Затем при наличии плана начинается его загрузка истории.
- Повтор истории использует только ID актуального плана. Старое уведомление
  с бесполезной кнопкой на дне без плана больше не остаётся.

До исправления воспроизведён переход после HTTP 503 истории на день без плана:
на экране оставалась ошибка предыдущего плана. После исправления проверены день
без плана, другой день с планом, другой сотрудник, возврат к исходному плану,
успешный повтор после временной ошибки, поздний успех и поздняя ошибка старого
запроса истории.

## Оставшиеся ограничения и риски

1. Первопричина реального инцидента руководителя в production всё ещё не
   установлена. `/distributions` не объявляется доказанной причиной. Здесь
   исправлены воспроизводимые дефекты клиента.
2. Проверки выполнены в локальном Edge, не в настоящих Telegram WebView Mac/iOS.
   После отдельно согласованного развёртывания потребуется проверка на реальных
   устройствах и с реальной авторизацией.
3. Таймаут POST/PATCH не доказывает отсутствие commit на сервере. Сохранено
   предупреждение и правило сначала обновить данные, а не автоматически
   повторять изменение. Исправление A02 не является серверной идемпотентностью
   всех операций.
4. Валидация строже прежней для неверных типов и небезопасных URLs. Если в
   реальных данных есть такие значения, раздел покажет ошибку. Старые корректные
   отчёты и отсутствие необязательных новых полей проверены искусственными
   fixtures; рабочая база для этого не открывалась.
5. Прочие замечания `PROJECT_AUDIT.md` остаются без исправлений. В частности,
   обработка некоторых исключений импортёром, старый путь Docker-сборки,
   ограничения RAM, объём истории и серверная конкурентность не входят в этот
   frontend-хотфикс. Их решение требует отдельного выбора объёма работ.
6. Не выполнялись Docker-сборка, production-миграции, проверка Ubuntu/Nginx,
   обновление зависимостей или действия с Bitrix24. Для согласованного
   исправления A02/A09/A10 они не нужны.
