## 2. Предлагаемая окончательная политика доступа

**Рекомендуется согласовать независимые каналы входа при общей идентичности.**
Web-вход требует существующий employees.id, employees.active=1, активную
web_credentials и действительную сессию. Роль берётся из employees на каждом
запросе; переданные клиентом employee_id/role не определяют текущего пользователя.
Менеджер работает только со своими объектами, supervisor — в пределах прежних
прав отдела. Общие Store.owner/revision/locked/closed/goal правила сохраняются.
Web-учётка не создаёт нового employee и не назначает роль supervisor.

Telegram-канал остаётся как сейчас: HMAC initData + bot ACL/access.db либо
существующее исключение для bot admin + active employee. Для web **предлагается
не требовать Telegram ID и bot ACL**, поскольку рабочий desktop-вход должен быть
самостоятельным. Это изменение политики относительно предложенного ранее
сохранения ACL для web, поэтому без явного принятия владельцем не внедряется.

| Действие | Предлагаемое последствие |
|---|---|
| Отключить employees.active | Запрет обоих каналов на следующем запросе, отзыв web-сессий |
| Отключить web_credentials.active | Только web; Telegram не меняется |
| Удалить доступ /removeuser в боте | Только Telegram по его прежним правилам |
| Заблокировать бота в Telegram | Не меняет web-доступ автоматически |
| Изменить роль сотрудника | Следующий web-запрос использует актуальную роль |
| Изменить/сбросить web-пароль | Отозвать все web-сессии; Telegram не меняется |

Альтернатива для выбора владельцем: оставить дополнительное требование bot ACL
и Telegram-привязки для первого web-релиза. Она проще повторяет прежнюю политику,
но не допускает самостоятельный web-доступ без Telegram. Не применять оба
варианта одновременно или неявно выбирать по наличию заголовка.

## 3. Сессии, пароли и ограничения — предлагаемые значения

- Argon2id, индивидуальная соль, PHC hash; начальный минимум 19 MiB, t=2, p=1.
  Библиотека/версия фиксируются будущим auth-PR; стандарт не реализуется вручную.
  До production нужен замер на новом VPS. Не более двух дорогих hash-проверок
  одновременно на экземпляр приложения, ограниченная очередь/429 при перегрузке.
- Пароль: минимум 15 символов для однофакторного входа, максимум 128 символов
  плюс ограничение размера UTF-8 тела. Разрешены пробелы/Unicode, без обрезания,
  принудительного периодического изменения и выдуманных правил состава.
  Конкретный лимит/UX также требует принятия; не выводить пароли в аудит.
  Ориентир минимальной длины — [NIST SP 800-63B-4](https://pages.nist.gov/800-63-4/sp800-63b.html#passwordver).
  В будущем добавить локальную проверку распространённых/скомпрометированных
  паролей без отправки введённого пароля внешнему сервису; версии списка фиксировать.
- Непрозрачная сессия: CSPRNG 32 байта; в БД только SHA256 случайного токена,
  credential/employee binding, generation, timestamps. Сессии не содержат роль
  как доверенное право. Ротация после входа/смены пароля, немедленный отзыв.
- Cookie: `__Host-planner_session`, Secure, HttpOnly, SameSite=Strict, Path=/,
  без Domain; один HTTPS origin для web и его API. Нет JWT/localStorage/URL токенов.
- Абсолютный срок **12 часов**, бездействие **30 минут**, «запомнить меня» нет.
  Фоновые polling/health запросы не продлевают бездействие. Способ передачи
  признака пользовательского действия ограничить известными маршрутами; не
  доверять любому клиентскому заголовку как продлению без ограничений.
  last_seen обновлять не чаще раза в 5 минут, сохраняя консервативную проверку
  expiry (возможен немного более ранний выход, никогда продление сверх лимита).
- Выход/истечение сессии не останавливают и не дублируют серверный таймер.
  Неуспешное сохранение не повторять автоматически после нового входа; сначала
  загрузить актуальное состояние/ревизию и показать неопределённый результат.
- Сессионный CSRF token в X-CSRF-Token + Origin/Fetch Metadata; login защищён
  отдельным коротким pre-auth контекстом (5 минут), после входа он отзывается.
  SameSite не заменяет CSRF; нет мутаций через GET и wildcard credential CORS.
- Начальные лимиты: 5 неудач на login / 15 минут, 20 на IP / 15 минут,
  Retry-After/429, без вечной блокировки аккаунта. Учитывать общий офисный NAT;
  параметры проверить нагрузочно. Общие ограниченные SQLite-счётчики, не dict
  процесса; IP заголовки только от явно доверенного reverse proxy.
- Одинаковое сообщение для неизвестного/отключённого login, dummy hash, аудит
  без пароля/cookie/полного initData. Удаление истёкших служебных записей пакетами,
  срок хранения login_attempts предлагается 24 часа. Retention auth_audit отдельно
  согласовать до production; не вводить бессрочное хранение сырых IP.

Базовые источники для будущей реализации: [OWASP Password Storage](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html),
[Session Management](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html),
[CSRF Prevention](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html).
Числа TTL/лимитов/retention выше — предложение проекта, не результаты измерений.

## 4. Создание и сброс паролей руководителем

Открытой регистрации нет. Supervisor после повторного ввода собственного пароля
может создать web-учётку только для существующего активного manager, отключить
её или инициировать reset. employee_id UNIQUE, нормализованный login UNIQUE;
автоматического изменения employees/role/Telegram/Bitrix-привязок нет.

Предлагается одноразовое приглашение/reset с 32-байтовым секретом и сроком
30 минут; в БД только hash, purpose, employee binding, expires/used/issued_by.
Руководитель получает его однократно и передаёт сотруднику лично по заранее
согласованному каналу. Не отправлять секрет ботом/почтой автоматически.
Сотрудник сам задаёт постоянный пароль; руководитель его не видит.
В интерфейсе reset-код вводится в форму, не передаётся в URL/логи/аналитику.
Погашение одноразовое и транзакционное; reset отзывает действующие сессии и
предыдущие приглашения. Защита CSRF/rate limit действует и здесь.

Bootstrap первого web-supervisor — отдельная защищённая локальная админ-команда
с подтверждённым existing employee_id и скрытым вводом пароля, в согласованное
окно. Не создавать default password и публичный bootstrap endpoint. Через
обычный manager-account CRUD запрещено создавать/сбрасывать supervisor.
Восстановление supervisor и защита последнего доступного руководителя — отдельный
операторский сценарий, без повышения роли администратору бота.

Канал передачи одноразового кода, TTL приглашения и полномочия руководителя на
такой reset требуют явного согласования. До этого — проект, не рабочий механизм.

## 5. Возможная миграция 4→5 и откат

Миграцию **не запускать** до отдельного решения. Добавить таблицы в ту же
planner.db: web_credentials, web_sessions, web_login_attempts, web_auth_audit,
web_password_actions (invitation/reset). Все identities ссылаются на employees;
планы/задачи/таймеры/согласования/закрытые отчёты/старый аудит не переписываются.
Роли не дублируются в credentials. Не создавать отдельную базу планов.

Применение после согласования — одна транзакция с version/checksum registry,
индексами/UNIQUE/FK и user_version=5 только при успешном завершении. Повторный
запуск безопасен; неизвестная новая схема отвергается; ошибка откатывает весь шаг.
На этапе реализации — только отдельные синтетические базы schema4 и внедрённые
сбои, без копирования рабочих SQLite и без миграций на Ubuntu.

**Проблема отката:** исходный 2.1.1 понимает максимум schema4; он не откроет 5.
Простое возвращение его образа не является допустимым rollback после миграции.
Предпочтительный порядок будущего релиза:

1. Отдельно подготовить и проверить compatibility bridge: прежняя Telegram
   логика, auth выключена, знает строго определённую additive schema5; на schema4
   сам новых таблиц не создаёт. Согласовать и сохранить этот rollback-артефакт.
2. Создать проверенные Backup API копии/restore trial в согласованное окно.
3. Выпустить auth/schema5 только после принятия bridge и тестов сохранения данных.
4. При ошибке отозвать/выключить web-вход и вернуть bridge image, **сохраняя
   текущую schema5**, новые планы/факт/отчёты и старый Telegram сценарий.

Это предложение bridge-PR, не уже поддержанная совместимость. Альтернатива —
восстановление schema4 backup в новый каталог; оно исключает последующие записи
из активного представления. Перед таким решением сохранить текущую БД/очередь,
согласовать перенос данных/простой. Обратная миграция и обещание «без потерь»
одной командой не допускаются. Данные auth-аудита также не выбрасывать молча.

## 6. Маршруты и повторное использование

Telegram /api/... с HMAC не меняется. Web /api/web/auth/... и /api/web/accounts/...
имеют явные cookie/CSRF зависимости. Web business router /api/web/plans,
tasks, requests, reports, history, distributions возвращает те же DTO и вызывает
те же Store-методы через общий внутренний actor. Не копировать SQL/правила целей.
Не принимать cookie в Telegram API или initData в web API как fallback.

Общие операции вынести в небольшие функции/router factory с разными actor
dependencies; сначала regression Telegram без изменения контрактов. Будущий
общий frontend transport принимает способ auth явно, сохраняет deadline JSON,
runtime validation, отмену, stale-context guards и отсутствие повторов POST/PATCH.
Не подключать существующий demo к настоящему API переключателем роли.

Планируемые маршруты: csrf, login, me, logout, password, accounts create/list/
disable/reset, invitation redeem и бизнес-операции. GET csrf/me не раскрывают
списки сотрудников без сессии. Весь account-admin аудит фиксирует реального
supervisor; системные отзывы не выдаются за действия менеджера.

## 8. Тесты безопасности и совместимости

- Матрица: manager свой/чужой employee/plan/task/request/report/notices; supervisor
  отдел, bot admin без supervisor; inactive employee/credential, смена роли/ACL.
- Неверный пароль/неизвестный login, защита от enumeration, лимиты/NAT/proxy-IP,
  одновременные проверки, bounded CPU/RAM и SQLite busy/lock без утечки секретов.
- Expiry по контролируемым часам, idle/polling, абсолютный срок, fixation,
  rotation/logout/reset/disable/revoked token в нескольких процессах.
- Все cookie flags, CSRF/Origin/Fetch Metadata и login CSRF; cookie/initData не
  переходят в другой канал; секретов нет в URL/storage/logs/ошибках.
- Одноразовый invitation/reset: повтор/параллельное погашение, expiry, неверный
  employee/purpose, отзыв прежних сессий, сохранение реального инициатора в аудите.
- Schema4 synthetic fixture со всеми сущностями: 4→5, повтор, внедрённый сбой,
  FK/integrity, backup/restore и bridge rollback с сохранением новых результатов.
- Telegram regression, ревизии и неопределённый исход POST timeout, один серверный
  таймер между двумя интерфейсами, confirm idempotency и неизменяемые отчёты.
- HTTPS browser fixtures для настоящих Secure/CSRF cookies; не ослаблять эти
  флаги ради dev и не засчитывать старый demo-тест как проверку реального login.
- Production build без demo; при выключенном WEB auth новых маршрутов/доступа
  нет. Никаких реальных пользователей, CRM, токенов или рабочих SQLite в тестах.

## 9. Что требуется принять владельцу

1. Независимый web-доступ от bot ACL по §2 либо дополнительный Telegram ACL.
2. Сессии 12 ч / 30 мин бездействия без продления polling и без remember-me.
3. Supervisor приглашает/reset только manager; постоянный пароль выбирает сам
   сотрудник; срок кода 30 минут и защищённый личный канал передачи.
4. Additive schema5 плюс отдельный rollback bridge вместо обещания возврата
   старого 2.1.1 на schema5; этапность и критерии тестов выше.
5. Предложенные password/rate/concurrency/retention значения и будущий HTTPS
   origin. Замеры нового сервера и аудит security-тестов — отдельная приёмка.

До этого решения нет ветки реализации web-auth-foundation, кода авторизации,
новых таблиц/миграций или серверных действий. Файл базы знаний в ChatGPT
необходимо обновлять отдельно после принятия документации в Git.
