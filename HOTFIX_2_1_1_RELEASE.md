## Сборка

Исправления A01/A02/A09/A10 уже находятся в исходном срезе; повторно не
переписываются. A19: добавлен независимый planner-only профиль с уникальным
release ID, Git SHA, манифестами, списком файлов и SHA256. Существующие вызовы
stage1 и `--stage2` сохранены, исторические артефакты не заменяются.

Исходники упаковки должны быть закоммичены. Из корня, на согласованном release
коммите, с локально установленными зависимостями pnpm из frozen lockfile:

```powershell
.\.venv\Scripts\python.exe -B deploy/package_release.py --planner-only --release-id planner-2.1.1-rc1-20261021
```

Для другого выпуска всегда выбирать новый ID. Упаковщик сначала выполняет
offline frozen install и production build, проверяет lockfile и статику,
собирает и проверяет архив во временном каталоге. Не отключает проверки
зависимостей. При неполном локальном кеше требуется отдельная установка
зависимостей из lockfile; никакой загрузки npm в Docker нет.

Выход: `deployment-artifacts/ИМЯ.tar.gz`, `.tar.gz.sha256`, `.tar.gz.files.txt`.
Внутри `frontend-build.json` и `release-files.json`: согласованные release/Git SHA,
хеши assets, lockfile и остальных файлов. Старые пути package API и `--stage2`
совместимы. Манифесты доказывают целостность, но не являются цифровой подписью.
Проверка после распаковки: `python -B deploy/release_check.py`.

Архив включает backend planner, access.py (для чтения ACL), Python-зависимости,
Compose planner, Python Dockerfile и готовые assets; не содержит bot.py, bot
Compose/Dockerfile, новых web-исходников, demo, SQLite, .env, maps или токенов.
Безопасный planner.env.example содержит лишь технические настройки, не секреты.

В копии planner.env.example внутри нового архива PLANNER_IMAGE получает тег
этого release ID; BOT_RELEASE_IMAGE удалён. Исходный исторический шаблон в Git
не изменяется. Реальный .env не читается и не генерируется упаковщиком.

## Будущая установка — только после отдельного разрешения

20.10.2026 администратор перенёс приложения на новый сервер; старый удалён,
по сообщению владельца. Старые пути, ресурсы и конфигурации **не проверены**.
Ниже шаблон порядка, а не готовая команда для нового сервера.

1. Получить только read-only сведения: контейнер planner и его image/digest,
   project labels, UID/GID, mounts, реальные пути planner.db/access.db/очереди,
   journal mode, свободные диск/RAM, занятые порты. Не печатать env/токены.
2. Подтвердить schema 4, текущее состояние и readiness, активные таймеры.
   Определить окно переключения, сохранить старый образ и конфигурацию.
3. Через SQLite Backup API создать и проверить копии planner и очереди. Не
   копировать живой db отдельно от журналов; тестовое восстановление — в новый
   каталог. Базы, ACL, очередь и .env не заменять локальными файлами.
4. Скопировать архив и SHA256, проверить checksum до распаковки. Использовать
   новый каталог выпуска и новый тег образа, например соответствующий release ID.
   Не перезаписывать существующие каталоги или теги.
5. В новом каталоге проверить `release_check.py`, затем статический Compose
   config без вывода секретов. Использовать `deploy/planner-compose.sh` с
   проверенными переменными из новых серверных сведений; schema остаётся 4.
   Выполнить Linux RO/RW smoke на синтетических данных, если отдельно согласован.
6. Собрать **только planner** через `sh deploy/planner-compose.sh build planner`.
   После разрешения на переключение: `sh deploy/planner-compose.sh up -d
   --no-deps --no-build planner` (одна команда). Не выполнять compose down/prune,
   не менять bot, Nginx, чужие сервисы, токены, порты или webhook.
7. Проверить healthz 200, API 401 без initData, ops readiness, целостность assets,
   прежнюю schema/данные, manager/supervisor, выбор двух менеджеров, загрузки,
   таймеры, согласования, закрытые отчёты и восстановление импорта. Реальное
   распределение не подтверждать ради теста; изолированная цепочка — временная.
8. Проверить Telegram WebView на macOS/iOS и реальных сотрудников после отдельно
   разрешённой установки. Сравнить ID/StartedAt посторонних контейнеров до/после.

## Откат

Сохранить текущее состояние planner/queue и журналы даже при ошибке. Вернуть
прежний сохранённый образ planner и прежний каталог/настройки, без пересборки
бота. При подтверждённо совместимой schema 4 оставить текущую planner.db:
этот релиз не требует миграций или восстановления старой базы.
Не выполнять обратную миграцию, не удалять очередь и не откатывать access.db.
Если восстановление копии всё же необходимо — только отдельное согласование,
новый каталог и проверка. **Старая копия не содержит записи после её создания**;
сохранение актуальной БД не выполняет их автоматическое объединение. До restore
согласовать сохранение/перенос новых планов, факта, таймеров, отчётов и истории.
Повторить health/roles/history/queue проверки. Старые образы/архивы не удалять.
