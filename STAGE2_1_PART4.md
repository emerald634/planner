## Механизм синхронизации

Если DISTRIBUTION_QUEUE_PATH задан, FastAPI lifespan создаёт один цикл на процесс
после миграции planner.db. Первый проход сразу, дальнейшие каждые 30 секунд
после окончания предыдущего. Такой интервал даёт небольшую нагрузку для
утреннего распределения; появление в уже открытом UI может занять до следующего
30-секундного обновления интерфейса дополнительно. После перезапуска очередь
перечитывается, распределения сверяются с inbox по UUID/SHA256.

Без пути функция отключена. Подтверждающие пользователи задаются отдельно через
DISTRIBUTION_CONFIRMER_IDS; пустой список не даёт права ни администратору,
ни supervisor автоматически. На VPS настройки пока не добавлялись.

Очередь открывается mode=ro, query_only, resolve(strict=True): отсутствующий файл
не создаётся. Соединение закрывается до записи в planner.db. Mini App никогда
не вызывает initialize/publish очереди. Работа выполняется в отдельном потоке,
не блокируя обработку HTTP. При остановке coroutine отменяется; уже начатая
короткая SQLite-операция может завершиться в рабочем потоке, её транзакция остаётся
атомарной. В production остаются прежние таймауты SQLite, без дополнительных
сетевых портов, polling Telegram или CRM-запросов.

Ошибки чтения не останавливают Mini App: безопасное сообщение в лог, повтор через
30 секунд. Payload, содержимое исключения, путь и секреты в новые логи не попадают.
Отдельная ошибочная запись сохраняется в import_attempts со status=error,
числом попыток и временем; остальные записи продолжают обрабатываться.
Повторные попытки происходят автоматически. Неустранимую ошибку не очищаем и
не объявляем успешной: руководитель видит сообщение о повторении импорта.

Успех/review хранится в distributions атомарно с задачами. Диагностическая
import_attempts обновляется отдельно: если процесс завершится после commit,
следующий проход восстановит диагностику по distributions без повторных задач.
BEGIN IMMEDIATE/уникальные ограничения защищают параллельные процессы.
Неактивные и конфликтующие привязки требуют отдельного рассмотрения;
состояние review не применяется впоследствии автоматически.

## Интерфейс и права

На задаче отображаются источник «Утреннее распределение», назначенные даты,
количество и статус. ID лидов остаются в БД, новые API не возвращают их.
Менеджер подтверждает свой draft; после approved видит «Подтверждён» и сохраняет
таймеры/факт/результат. Импортированное количество защищено прежними backend
правилами. Плановое время изменяется через существующее согласование.

Для approved/closed импорт оставляет планы/отчёты неизменными, появляется
«Требует рассмотрения» с причиной и назначением. Менеджер получает только свои
связанные записи. Supervisor видит отдел и ошибки импорта. Если сотрудник
сменил Telegram/Bitrix привязку, прежний snapshot не раскрывается новому
пользователю этой записи. Supervisor получает общее уведомление о неразрешённой
привязке без клиентских данных. Доступ API через прежний initData/ACL/роль,
неавторизованный запрос получает 401; новый незащищённый API не добавлялся.

## Миграция и проверка

Схема planner.db 4: добавлена только import_attempts и запись schema_migrations,
в той же транзакции. Другие данные не перезаписываются. Backup API поддерживает
1/2/3/4. Старые проверки миграции/сохранности истории продолжают проходить.
Не запускать текущий backend с рабочей БД до согласованного обновления:
Store.initialize автоматически выполняет миграцию при старте.

Полный набор: 137 Python-тестов успешно, включая 7 новых сценариев sync.
React: tsc --noEmit и Vite production build успешно.
Edge/Playwright: оба сценария ui.cjs и ui-distributions.cjs успешно.
Проверены автоимпорт, retry, рестарт, параллельность, повреждённая запись,
read-only очередь, восстановление диагностики, draft/approved/closed,
сохранность отчёта, запрет чужих данных, источник задачи, менеджерское
подтверждение и таймер, supervisor review. Все БД временные, токены искусственные;
действующая CRM/Telegram не использовались. Локальные тестовые серверы остановлены.

## Ограничения перед финальным релизом

Docker/Compose не редактировались. Нужны отдельно согласованные включение новых
модулей в образ бота, RW bind очереди у бота/RO у Mini App, одинаковые UID/GID,
права папки и проверка DELETE journal при живом writer на Ubuntu. Docker локально
нет. Пока нет нового production-архива и команд применения к серверу.

Активность в боте пока явная конфигурация; live-обмен active с Mini App не
реализован. Импорт независимо проверяет активность и не создаёт частичные
распределения при отключённом менеджере. Нет процедуры замены распределения,
разрешения review или изменения количества. Постоянные ошибки повторяются
каждые 30 секунд; их нужно разобрать перед финальным релизом. Цикл читает
историю очереди целиком; для небольшого ежедневного потока этого достаточно,
архивацию/пакетное чтение при росте истории согласовать отдельно.

Рабочие .env/access.db, Dockerfile/Compose не менялись, bot.py/config.py этой
частью не изменялись. Сервер Ubuntu, Nginx, контейнеры, данные Bitrix24 не
затронуты. К пятой части и развёртыванию переходить только после разрешения.
